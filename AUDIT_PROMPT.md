# Mission

You are performing an **exhaustive forensic security, correctness, and quality audit**
of the `My-Lists-Addon` repository — a single-deploy Cloudflare Worker that serves both
a Stremio/Nuvio/Wako add-on backend API and a large vanilla-JS web UI. Your job is to
find **every** bug: backend logic, API routes, auth, data integrity, frontend client
code, UI rendering, accessibility, performance/limits, and build/CI integrity.

This is a **report-first audit**. Do not fix anything unless I explicitly tell you to.
Produce evidence-backed findings.

## Absolute constraints (violating these fails the audit)

1. **NEVER edit `worker_entry_combined.js`.** It is generated by `python build.py`
   from `header.js` + `00_*.js` … `57_*.js`. Any edit there is destroyed on the next
   build and is invisible to the drift check. If you ever need a fix applied, it goes
   in the numbered sources, then `python build.py && python check_sync.py`.
2. **No refactors, no modernization, no style churn.** Pure vanilla JS. Do not
   convert to classes/TS, do not reorganize files, do not rename anything, do not
   "improve" working code. Report only.
3. **Read before you claim.** Every finding must cite `file:line`. If you did not
   read the code path, you may not file the finding. Prior audits in
   `docs/history/` contain corrections where an auditor filed a bug without reading
   it — do not repeat that.
4. **No live side effects.** Do not deploy, do not call third-party APIs (Trakt,
   TMDB, Simkl, MDBList, JustWatch…), do not touch real KV/D1/R2, do not push
   branches other than the current one, do not commit unless asked. All experiments
   run against the repo's own in-memory harnesses. Never exfiltrate or publish any
   credential you encounter — if you find one, report it as a P0 and stop.
5. **Preserve shared scope.** If you propose any fix, it must not introduce a
   duplicate top-level `const`/`let`/`function` name across the numbered files.
6. **Minimal diffs** if and when fixing is authorized: targeted changes only.

### Audit dimensions (every one must be explicitly covered in your report)

**A. Routes & request handling.** For every route: method allow-list (does a GET
mutate? does POST/OPTIONS/HEAD behave?), unhandled methods, 404/405 correctness,
path traversal (`../`, encoded `%2e%2e`, null bytes, over-long UTF-8), query-string
abuse (duplicate params, huge values, type confusion), unvalidated redirects,
error handlers that leak stack traces/internal hostnames/keys, routes reachable
without the auth they assume. Fuzz every parameterized route with hostile payloads.

**B. Authentication & authorization.** Creator-key auth, admin session/cookie auth
(forged signature, expired, algorithm confusion, logout semantics), and above all
**tenant isolation**: can account A read or mutate account B's data through *any*
route, including ones that look public (`/api/preview`, `/api/resolve`,
`/api/save`, `/lists/:user/*.json`, `/api/public-lists.json`, share links, the
short-config `/api/save` id path)? Build an auth matrix: every protected route ×
{no auth, wrong key, *another account's* key} — all must reject. Check anonymous
paths that accept an identifier and serve personal data.

**C. Injection & escaping.** Template-literal HTML is the highest-risk area:
- `</script>` breakout in the inline client bundle and in server-rendered pages
  (list names, item titles/posters, display names, `serverEntries`, OAuth/key
  fields, install links). `JSON.stringify` escapes `"` and `\` but **not** `</script`.
- Reflection context per field: script body vs. HTML attribute vs. URL vs.
  ld+json — each needs different escaping.
- SSRF: any route that fetches a caller-supplied URL (host allow-list? redirect
  following? response echoed? rate-limited?).
- Prototype pollution via deep-merge/`Object.assign` on request bodies.
- Header injection, CSV/formula injection in exports, SQL injection in any
  hand-built D1 statement (vs. bound params).
- CSP presence and correctness on every served page; service worker scope.

**D. Data integrity & storage.** D1/KV/R2/Queues interactions: lost updates,
read-modify-write races under concurrency (parallel saves/likes/pushes), KV
eventual-consistency windows, upsert vs insert (duplicate-key rollbacks that report
`{ok:true}` while discarding data), tombstones vs hard deletes, resurrection of
deleted records, migration windows and dual-read/dual-write paths
(`migrations/`, `FF_V2_LISTS_*`, `FF_EVENT_TRACKING`, activity shard cutover),
backfill jobs clobbering live data, cache poisoning, cross-account index entries,
byte/row-size limits (UTF-16 units vs bytes), queue retry/DLQ behavior, cron jobs
that damage or resurrect state on second tick (test with a **fresh isolate**, not a
warm module cache).

**E. Backend correctness.** Plain logic bugs: wrong key derivation (e.g.
`sKey.split(':')[0]`-style prefix mistakes), off-by-one in pagination/caps, wrong
defaults, wrong unit conversions, bad dedupe, inverted conditions, swallowed errors
(`catch {}` that report success), race between check and use, timezone/date math,
`NaN`/`undefined` propagation into responses, incorrect cache keys/collisions.

**F. Providers & OAuth.** Trakt, TMDB, Simkl, MDBList flows: OAuth `state`
validation, PKCE, callback id-confusion, token rotation that reports success when
the D1/KV write failed (new token dead, leaked old token still valid), refresh
races, the provider breaker (open/half-open transitions), rate-limit and budget
handling, provider response shape changes, secret leakage into responses or logs.

**G. Frontend client code (`16_`–`24_`).** This is the largest surface and the
least covered by past audits. Hunt for: client/server contract mismatches (client
omits a field the server's conflict guard needs; client ignores a response field),
**false success** (UI shows "saved" on 401/409/500), requests never sent
(missing binding, dead call site), dead code, phantom DOM ids read from
`localStorage` or `getElementById` that blank a whole tab, unhandled promise
rejections, state desync between local and server copies, lost deltas on 409
conflict, XSS via `innerHTML`/`insertAdjacentHTML`/`eval`-adjacent sinks, and
keyboard/gesture handlers that do nothing.

**H. UI, rendering & accessibility.** Every page must render and every inline
`on*` handler must resolve to a defined function. Check: the builder page, the
shell variant (`FF_NEW_UI`), the admin dashboard, the service worker, and each with
**hostile input** (every caller-supplied field set to an XSS payload). Check the
three contexts a field can land in (script body / attribute / URL). Accessibility:
focus management, `aria-*`, keyboard reachability, contrast, native
`alert()/confirm()/prompt()` usage, duplicate control semantics.

**I. Performance & platform limits.** Per-invocation KV ops, D1 queries, outbound
subrequests, and CPU against Cloudflare's caps (free: 50 subreq / 10 ms CPU; paid:
10,000 / 30 s) — measure at realistic scale (e.g. 100 → 20,000 list index entries,
400 accounts, 500–1,200 lists per creator). Cache headers (`max-age` on
per-account GETs = privacy/DoS bug), rate limiting on every expensive or anonymous
route, N+1 query patterns, unbounded loops over KV `list()`, bundle size budget,
memory growth per request.

**J. Build, CI & deployment integrity.** `python check_sync.py` byte-exactness,
`FUNCTION-MAP.md` drift, scope-checker coverage gaps (identifiers that resolve in
the combined file but not per-source), `.github/workflows/` gaps (does CI render
*all* template-literal pages? all three? the service worker? the hostile variant?),
`html_checks.py` blind spots, `wrangler.toml` vs. dashboard-set bindings/vars,
secrets accidentally committed (search history for tokens/keys — report, don't
print).

## Method & evidence standard

For every dimension above, do all three: **(1) read the source**, **(2) probe it
executably where possible**, **(3) only then file it.**

Use the repo's own harnesses — do not build new infrastructure:

- `tests/harness.mjs` — in-memory Worker harness. D1 is backed by **real SQLite**
  (`node:sqlite`) loaded from the committed `schema.sql` with `PRAGMA
  foreign_keys = ON`; `makeKv()`, `freshIsolate()` (cold-colo simulation), and
  `failWhen(fn)` (fault injection: make D1/KV throw) are available. A constraint
  violation here is the constraint violation D1 would raise.
- `tests/client-harness.mjs` — runs the client bundle against a DOM stub so its
  logic (payloads, response handling, state transitions) can be tested directly.
- `render_check.js` — renders the builder page / `--shell` / `--admin` / `--sw` /
  `--hostile` variants to disk for `html_checks.py` and `scope_check.mjs`.
- `node --test tests/*.test.mjs` — the existing suite; read it to learn the idioms
  and to find what is *not* covered.

**Executable proof is required for every CONFIRMED finding.** Write each probe as a
standalone Node 22 script following the existing convention in `audit/`:

- Create `audit/<slug>-<date>/` (e.g. `audit/full-<YYYY-MM-DD>/`), one probe per
  finding named `pNN_<topic>.mjs`.
- Each probe must be runnable from the repo root, write nothing outside the
  in-memory harness, contact no external service, and modify no repository state.
- Add a `README.md` in that directory with a table: `Probe | Finding | What it
  demonstrates` — matching `audit/full-2026-09-13/README.md` exactly in style.
- Include **negative controls**: probes that prove a suspicious area is actually
  clean. They are as valuable as positive ones.

### Finding format

Write the report to `docs/history/AUDIT-<YYYY-MM-DD>-<SLUG>.md` (do not overwrite
existing audit files) with:

1. **Executive summary** — overall health, the single most dangerous issue, honest
   statement of what resisted probing.
2. **Findings-by-severity table** — counts by P0–P3 + Informational.
3. **Per-finding sections**, each with:
   - **ID** (`SEC-`, `BE-`, `FE-`, `DB-`, `CF-`, `PROTO-`, `A11Y-`, `PWA-`,
     `API-`, `UI-`, `PERF-`, `INFO-` + zero-padded number)
   - **Severity** (P0 Critical / P1 High / P2 Medium / P3 Low / Informational)
     with a one-line justification of impact
   - **Status**: `CONFIRMED` (runnable probe committed, cite the path) or
     `SUSPECTED` (source reading only — cite `file:line` and the exact reasoning)
   - **Location**: `file:line` (in the *numbered sources*, not the combined file)
   - **Description**, **Impact / attack scenario**, **Reproduction** (exact command)
   - **Suggested minimal fix** (in the numbered sources, respecting shared scope)
4. **Probe index** table.
5. **Coverage statement**: which of dimensions A–J you covered, how, and what you
   could *not* cover and why.

Severity guide: **P0** = unauthenticated data exposure / credential exposure /
remote code execution / total auth bypass. **P1** = authz gap, data loss/corruption,
stored XSS, silent failure that discards user data. **P2** = correctness bug with
workaround, DoS, missing rate limit on expensive route. **P3** = minor correctness,
UX-breaking defect, perf. **INFO** = hygiene, dead code, docs.

## Execution order (suggested)

1. Orient + `bash verify.sh` + build the route inventory.
2. Static sweep: read all 58 sources end to end with the dimension checklist in
   hand. File SUSPECTED findings as you go.
3. Route-by-route executable pass (dimensions A, B) using `tests/harness.mjs`:
   auth matrix, method matrix, fuzz.
4. Security pass (C): XSS sinks inventory, `render_check.js --hostile`, SSRF,
   prototype pollution, CSP.
5. Data-integrity pass (D): concurrency, fault injection via `failWhen`, fresh

6. Client pass (G) via `tests/client-harness.mjs` — contract mismatches, false

7. UI/render/a11y pass (H).
8. Performance pass (I) at scale, incl. `loadtests/`.
9. Correctness + provider passes (E, F) — targeted probes per SUSPECTED finding.
10. Build/CI pass (J).
11. Write the report + probe README; re-run `bash verify.sh` to prove you left the
    tree green; summarize findings by severity in your final message.

## Definition of done

- Every CONFIRMED finding has a committed, runnable probe in `audit/<slug>/` and a

- Zero edits to `worker_entry_combined.js`; zero fixes applied unless authorized;
  zero external calls; `bash verify.sh` still green.
- Report at `docs/history/AUDIT-<date>-<slug>.md`; final message = severity table +
