## Safeguards Already in the Code (do not remove or bypass)
These are deliberate. Several are "one place" mechanisms that cover the whole Worker, so they are easy to break by accident.

| Where | What it does |
|---|---|
| Top of `00_constants.js` | A module-level `console` that passes every log line through `redactForLog` (masks keys, tokens, Creator Keys). **Never declare another top-level `console`.** |
| `02_http-and-creator-utils.js`, `function fetch` | A module-level `fetch` guard. It strips edge caching from any request carrying `Authorization` (a real cross-user leak before), and gives every call without its own timeout a 30 s ceiling. **Never declare another top-level `fetch`.** |
| `02_`, `json()` / `jsonCacheable()` / `jsonPublic()` | JSON responses default to `no-store`. Public data opts in to caching with `jsonCacheable`; the Stremio routes do through `jsonPublic`. A new route that returns something personal must use plain `json()`. |
| `00_`, `INSTALL_CONFIG_FIELDS` | One definition of every install-link setting, used by `/api/save`, `resolveConfig`, `decodeConfig`, the configure page and the builder's save body. **Add a new setting here**, never by hand in one of those places. |
| `04_`, `entryAccountRequirement`; `16_`, `rowNeedsAccount` | The D-8 rule, on the server and in the page. A test (`the builder page and the server draw the line in the same place`) keeps them in agreement, so change both. |
| `00_`, `REQUIRED_SCHEMA_VERSION`; `02_`, `schemaWriteGate` | API writes are refused (503 "being updated") while the database is behind the code. A new migration must: <br>1. end with an `INSERT` into `schema_migrations`; <br>2. be added to `schema.sql` and `D1_SCHEMA_MANIFEST`; <br>3. bump `REQUIRED_SCHEMA_VERSION` if the code depends on it. <br>See `docs/OPERATIONS.md` §4. |
| `04_`, `resolveConfig(config, env, { withTracking })` | Reads a person's tracking record only when asked (the channel meta route and `/api/resolve`). Catalog rows must not ask. |
| `/<id>/configure` and `/api/resolve` | Never return provider keys or tokens. The `P1-T2` test probes every route for this. |
| `02_`, `getOrBackfillAccount(env, username, profile)` | The `accounts` row is a **mirror** of the creator profile (`creator:{u}` / `creators`), which stays the source of truth until Phase 10. Never trust `accounts.key_hash` on its own: authenticate with `authenticateCreator`, then sync the row from the profile. `deleteAccountRow` removes a row and everything under its id (sessions, installs, secrets, snapshots). |
| `27_`, the install move | A moved `cfg:` record carries `_install` and no secrets; `resolveConfig` puts them back (`applyLegacyInstallRecord`). Reads never depend on the flags. **Never write code that reads a `cfg:` record's keys directly**: go through `resolveConfig`. A new secret install field must be added to `INSTALL_SECRET_COLUMNS` (a test checks). |
| `28_`, `storeProviderConnection` | A signed-in OAuth callback stores the token and redirects to `/?connected=<provider>` with **no token in the URL**. It returns false (and the callback falls back to the old fragment redirect) when there is no session, no key or no table, so connecting never breaks. Never add a token to a redirect URL for a signed-in browser. |
| `02_`, `encryptToken` / `decryptToken` / `hmacLookupKey` | AES-256-GCM token encryption with key rotation (`TOKEN_ENCRYPTION_KEY`) and an HMAC-SHA256 blind index (`LOOKUP_PEPPER`). ## Traps in This Codebase
1. **Never edit `worker_entry_combined.js` by hand.** Edit the split files and run `python build.py`.
2. **Files `09_` to `24_` are inside a template literal** (the web page is rendered as one big string):
   - a backslash or `${` in client code must be escaped;
   - prefer `startsWith` / `split` over regular expressions;
   - `\n` in client code must be written `\\n`;
   - a regex literal's escapes are written doubled (`/\\s+/`), and a regex built from a **string** needs four (`new RegExp('\\\\b')`), because the browser's string literal cooks them once more. `tests/client-escapes.test.mjs` fails on a lone backslash in page code;
   - a `data-act-args` value is JSON, never code: pass the array itself and a real `"\n"`, not `jsStringArrayLiteral(...)` or `"\\n"` (08_ had both).
3. **All numbered files share one scope.**
   - Top-level names must be unique across files.
   - New server-only code goes in a new numbered file **after `26_`** (the next is `41_...`), never between `09_` and `24_`.
   - `25_` and `26_` are the **inside** of `handleFetch` (they share `request`, `env`, `path`, `authenticateCreator`). `27_installs.js` and `28_connections.js` come after the `export default` block, at module level, so they cannot see those; pass what they need. `tests/client-harness.mjs` renders the page from the code **before** `export default`, so page rendering must never depend on `27_`+.
   - Tests that load source files into a sandbox (`loadSourceFunctions`) and call `resolveConfig` must include `27_installs.js`.
4. **In `27_` onward, never write the words `export default` together, even in a comment.** Those files come after the Worker's real export, and `render_check.js` (a CI step) cuts the combined file at the *last* place the words appear, so the page checks break.
5. **Shell heredocs in this environment mangle `\\` sequences.** Write patch scripts to a file and run them, or use the file-editing tool.
6. **The test D1** (`tests/harness.mjs`, real SQLite) enforces D1's limits: 100 bound parameters, 2 MB per row, 100,000-byte statements. A query that trips these would fail in production too.
7. The preview harness (`.claude/launch.json` → `mylists-harness`, port 8787) loads the built Worker once at startup. **Restart it after every rebuild.**
8. **Run the suite both ways:** `node --test tests/*.test.mjs`, then `MLA_TEST_V2_LISTS_READ=1 node --test tests/*.test.mjs` (CI does both). With the variable set, `makeEnv` turns `FF_V2_LISTS_READ` on for every test; a test that sets the flag itself still decides.   - **P7-1 (Arena): a strict Content-Security-Policy, and no third-party requests left on first paint.** `script-src 'self' 'nonce-<one per response>'` -- `'unsafe-inline'` and `https://cdn.jsdelivr.net` are gone, so an injected `<script>` (or an `src` to someone else's server) is refused by the browser instead of running.   - **P7-2 (Arena): the admin dashboard's identity, its sessions and its log.** `ADMIN_KEY` and a self-contained cookie were the whole of admin identity: nothing was revocable, nothing was attributed, nothing was recorded (S-10). Three pieces, each optional on its own:
    - **Cloudflare Access first.** With `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD` both set, a valid Access token IS the sign-in and names a person (`access:<email>`), with no `ADMIN_KEY` needed. The header is only a header -- anyone who can reach the Worker can send one -- so `adminAccessIdentity` (03_) verifies the RS256 signature against the team's own certs (`https://<team>/cdn-cgi/access/certs`, cached 5 minutes per isolate) and then the issuer, the audience, the expiry and `nbf`. The **audience** is what stops a token minted for any other Access application in the same Cloudflare account from opening this dashboard. `FF_ADMIN_EMAILS` is an optional second lock on who may *use* it, separate from Access's policy on who may reach it. A rejection logs one line per distinct reason per isolate (`[admin] refused a Cloudflare Access token: audience`), which is how a misconfiguration is diagnosed.
    - **The key stays, as break-glass (D-24).** Deliberate: being locked out of your own dashboard is worse than a longer login page, and the login page now says when Access is on so a locked-out admin checks the right thing. Access sign-in works with no `ADMIN_KEY` at all.
    - **Sessions are rows (migration 0018).** The cookie is `<32 hex id>.<secret>`, only the secret's SHA-256 is stored, and `resolveAdminIdentity` tries Access, then the row, then the pre-P7-2 signed cookie -- which is unchanged, so a browser signed in before the deploy is not signed out, and a deployment with no D1 or without 0018 still signs in (a migration must never lock the owner out). `POST /admin/api/revoke-admin-session` takes `{id}` or `{all:true}`; `GET /admin/api/admin-sessions` lists them and marks the one asking; `POST /admin/logout` revokes the row rather than only dropping the cookie. Expired rows are swept on login and on listing; `last_seen_at` is written at most hourly per browser.
    - **The audit log is written in `isAdminRequest`** -- the one gate all 39 admin routes already pass through (D-26), so a new admin route is audited the moment it exists instead of when someone remembers. One row per authorized *mutating* request (a `WeakSet` on the request keeps it to one where a route checks twice), with actor, a stable action name (`ADMIN_AUDIT_ACTIONS`, falling back to the path), the request's identifying fields, IP, status. **Named fields only** (`ADMIN_AUDIT_BODY_FIELDS`, D-27): there is no code path that copies an unknown field, so a `creatorKey`/`adminKey`/`token`/`password` in a body cannot reach the log. The body is read from `request.clone()`, so routes still read it themselves. GETs are not audited except `/admin/api/migrate-accounts` (`ADMIN_AUDIT_GET_MUTATORS`, a GET that changes state). The table keeps the newest 5,000 rows; `GET /admin/api/audit` reads it and nothing writes it through the API.

  - **P7-3 (Arena): every rate limit is an exact D1 counter.**
    - **The problem with a KV counter.** Every limit in the Worker was `ratelimit:<bucket>:<ip>`: read the number, compare, write it back. KV serves reads from the edge cache for up to a minute and has no atomic increment, so a burst arriving in parallel -- which is what a script, a scraper or a password guesser is -- all read the same pre-increment value and all passed. The limit did not hold in the only conditions it existed for (S-13).
    - **One primitive, in `rate_counters` (migration 0015, already in `schema.sql`).** `consumeRateLimit` keeps its name, its argument order and its contract; `rateLimitCount` (02_) writes one row per `bucket:client:window` -- `scope` is exactly the string the KV key used to be (`adminlogin:198.51.100.7`, `connimport:a<accountId>`), `window_start` is the epoch ms the window began at, so **windows are aligned to the clock** rather than started by the first caller, which is what makes a spent counter one row a sweep can delete by `window_start`. The increment (`INSERT ... ON CONFLICT DO UPDATE SET count = count + excluded.count`) and the read-back are two statements in **one `batch`** -- one transaction, and D1 does not interleave batches -- which is the atomicity the KV version could not have. A `RETURNING` one-liner would be a round trip cheaper and was deliberately not used: the harness models D1's `run()`/`all()` split, and correctness matters more than one round trip.
    - **Spend first, or spend on failure.** `consumeRateLimit` spends then compares, so refused requests count too (the counter records what arrived, and hammering does not earn a fresh budget when it pauses). The credential endpoints -- `/admin/login` (10/min), `/api/creator/restore` (20/min), `/api/creator/forgot-username` (5/15 min) -- use the new `readRateLimitCount` + `noteRateLimit` pair instead: read, do the work, and spend only on a *failed* guess, because a correct key must never consume the budget that protects it (a refusal spends nothing, and the count staying at the ceiling is what keeps it refused). `cost` is how much one call spends: 1 for a request, the number of titles for `/api/details/batch`, `/api/bulk-resolve` and the Better Posters warm, whose real ceiling is someone else's quota.
    - **All 13 call sites converted** (9 `consumeRateLimit` callers, 8 inline KV blocks of which 4 became `consumeRateLimit` and 4 the read/note pair; `connimport` keys on the account). `/api/creator/create` keeps its deliberate order: the slot is spent **before** the uniqueness check, so two requests landing together cannot both find the name free -- a test proves it with two concurrent creates and exactly one success.
    - **No D1 is a degraded limiter, not a disabled one.** No `DB` binding (or no 0015): the counter is a Map in the isolate -- a burst from one client is still refused, several isolates each allow the full budget (looser, never unlimited). The old fail-open (pass when `CONFIGS` is unbound) is gone; a missing `CF-Connecting-IP` is refused at the route with 400 as before. A failed D1 counter logs `[ratelimit] D1 counter failed, falling back to this isolate's memory: <reason>` once per distinct reason (capped at 20), silent for the expected `no such table`.
    - **Sweeping, and the one optional migration.** Spent rows are deleted at most once every ten minutes per isolate on `ctx.waitUntil` (never on the request's path), keeping a day -- longer than the longest window (15 min). That delete filters `window_start`, which the primary key `(scope, window_start)` cannot serve, so `migrations/0019_rate_counters_window_index.sql` adds the one index it wants (`idx_rate_counters_window`, also in `schema.sql` and `D1_SCHEMA_MANIFEST`). Without it the sweep scans: slower, not wrong, so the index is optional.
    - **The WAF half is the operator's, and optional.** `docs/OPERATIONS.md` §6 lists the six routes the task named (plus `/api/save` and the create/restore/reset/forgot group) with thresholds, the dashboard's expression syntax and the Free-plan note ("one rule -- make it `POST /api/session`"). **Nothing has to be clicked for the code to work**, which is why the task's checkbox is closed on the code half.
    - **Tests:** `tests/rate-limit.test.mjs` (11, new) -- no `ratelimit:` KV key from any of four limiters with D1 bound or without it, two requests arriving together cannot both spend a budget of 1, ten guesses then the 11th refused (per client, not global), aligned windows and no bucket bleed, the memory fallback on a database with no `rate_counters`, a cold isolate sweeping a two-day-old row only, and a missing client IP still 400. Updated where they assumed KV: the rolling-window suite and the BYO-key ceiling test in `tests/worker.test.mjs` (a D1 row is seeded/rolled now), the KV-write-count test (10 writes, not 11 -- and 0 on a repeat), and `tests/csp.test.mjs` (counter read back from D1, refused half asserted through Analytics Engine, KV asserted empty of `ratelimit:`).
