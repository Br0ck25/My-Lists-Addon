brought back.

fail (DB-02, reproduced, not yet seen in practice); one query on the Lists
page reads the whole lists table each time (DB-03, one index fixes it); two
migrations do not write themselves into the migration record (DB-04,
harmless).

Fix first: correct the backup section of `docs/OPERATIONS.md` (DB-01 step 1),
then decide whether the backup should copy KV (Questions, 1). No real

## Findings

### DB-01 (Medium, Backup & Recovery, High): the daily backup leaves out install links, My Channels, presets and synced settings, which live only in KV
**What a user would notice.** Nothing today. If the KV namespace `CONFIGS`
were lost or wrongly bulk-deleted, every install link pasted into Stremio,
Nuvio or Wako would stop working, and every account would lose its My
Channels, its presets and its synced settings. The daily backup could not
bring any of them back, though `docs/OPERATIONS.md` says it is enough.
**Evidence.**
- `docs/OPERATIONS.md:155`: "The KV namespace has no built-in backup. With
  `FF_V2_LISTS_ONLY` and `FF_EVENT_TRACKING` on, lists and Watch History are
  in D1." That is the only reason given for not copying KV.
- `.github/workflows/d1-backup.yml` dumps `D1_DATABASE_ID` and
  `ACTIVITY_D1_DATABASE_ID` only. Nothing reads KV or R2.
- Every install link is written to KV only: `src/api/78_save-and-like-routes.js:296`
  `await env.CONFIGS.put(savedConfigKey(id), savePayload);` (`/api/save`,
  called by Generate, `src/client/24_client-backup-restore-presets.js:1980`).
  When a legacy link is later moved to D1, its config still stays in KV:
  `src/api/27_installs.js:558-560` "config_json stays "{}": a legacy install's
  config lives in its cfg: record". D-10 says these links never expire.
- An account's channels and presets are written to KV only:
  `src/api/69_creator-api-sync-routes.js:80`
  `env.CONFIGS.put(\`creatorsyncpresets:${auth.username}\`, serialized)` and
  `:138` `creatorsyncchannels:`. `grep -rn "INTO presets" src` finds nothing:
  the D1 `presets` table is never written (only deleted from, in
  `src/jobs/51_account-purge.js:83`). Synced settings are
  `creatorsync:${username}` (`src/api/68_creator-api-account-and-save-routes.js:366`).
- `docs/OPERATIONS.md:659` (§33) says "Take a backup first (the KV export in
  §5)", but §5 describes no KV export. The KV-to-R2 export
  (`/admin/api/export-kv-to-r2`, `src/admin/65_admin-api-routes.js:1070`) is
  manual, one prefix at a time, and writes into R2 on the same Cloudflare
  account, which nothing copies off Cloudflare either.
- Reproduced: no (needs production). Searched: `grep -rhoE "CONFIGS\.put\(" src`
  for every KV prefix written, then checked each user-data prefix for a D1 copy.
**Root cause.** The backup was designed when D1 was meant to hold all user
data after the v2 cutover (`docs/ARCHITECTURE.md`, "D1 is the source of truth
for all user data"). Install-link configs, channels, presets and the sync
blob never moved, so the backup's coverage and the docs' claim drifted apart.
**Fix.** Smallest safe change, in steps:
1. Correct `docs/OPERATIONS.md` §5 (and the §33 line) to say which KV
   prefixes hold data no backup covers: `cfg:`, `creatorsync:`,
   `creatorsyncpresets:`, `creatorsyncchannels:`, `creatorchannel:`,
   `channelshare:`, `creatorlistorder:` and, while `FF_V2_LISTS_ONLY` is off,
   `creatorlist:`.
2. Add a KV step to the daily workflow: a script beside
   `.github/scripts/d1-backup.mjs` that lists and reads those prefixes through
   the Cloudflare KV API (a token with *Workers KV Storage: Read*), writes
   them as JSON lines, and is encrypted and verified the same way. It needs
   one more secret (the namespace id) and the token scope widened; that is
   the owner's step.
3. Reuse the workflow's existing gpg, verify and upload steps for the new file.
**Test.** A unit test for the new script in the style of
`tests/d1-backup.test.mjs`: a fake KV API with keys under each listed prefix
and one cache key; the output must contain every listed prefix's keys and
values, and must fail the run if a page read fails. It must fail if a prefix
is dropped from the list.
**Risk.** KV list/read calls count against the account's KV operations;
`cfg:` may have many keys (one per install link ever made), so the script
must page and space out requests the way `d1ApiQuery` does.

### DB-02 (Low, Backup & Recovery, Confirmed): a sign-up or play recorded while the backup runs makes that day's backup fail
**What a user would notice.** Nothing. The owner gets a red "D1 backup" run
and no copy for that day.
**Evidence.**
- `.github/scripts/d1-backup.mjs:198-206` reads one table at a time, in
  creation order, over many API calls (`minIntervalMs = 260`); there is no
  single snapshot. A row added to a child table after its parent table was
  read is copied without its parent.
- `.github/scripts/d1-backup-verify.mjs:30` runs each statement on its own,
  with foreign keys on (Node 22's `DatabaseSync` default), so the orphan row
  is refused and the run fails.
- Reproduced: yes, in the scratchpad (`backup_race.mjs`): built a database
  from `schema.sql`, added an account and its session after `accounts` was
  read and before `sessions` was. `verifyDump` returned
  `"statement 50 refused: FOREIGN KEY constraint failed"` and
  `"sessions: 0 rows restored, 1 read from D1"`. The same shape exists for
  `list_items` (after `lists` and `media`), `install_secrets` (after
  `installs`) and, in the activity database, `watch_event_sources` (after
  `watch_events`: a play reported by a second app).
- Not seen yet in production: all 30 runs from 2026-10-05 to 2026-11-03
  passed (GitHub Actions run list). The runs start between 08:30 and 12:00
  UTC, not 04:17, because GitHub delays scheduled jobs, and each lasts about
  two minutes.
**Root cause.** The dump is a sequence of reads, not a snapshot, and the
verifier rightly refuses a file that would not restore.
**Fix.** In `dumpDatabase`, after all rows are read, re-read nothing; instead
write child rows whose parent is missing as a comment, or simpler: in the
workflow, on a verify failure caused only by `FOREIGN KEY constraint failed`,
run the dump once more before failing. The retry is the smaller change.
**Test.** Extend `tests/d1-backup.test.mjs` with the scratch case above: the
workflow-level retry (or the dump's own handling) must end with a file that
`verifyDump` accepts.
**Risk.** A retry doubles the API calls on a bad day; still far under the
1,200-per-five-minutes limit.

### DB-03 (Low, Query Efficiency, Confirmed): every signed-in lists load reads the whole `lists` table
**What a user would notice.** Nothing yet. The Lists page gets a little
slower, and D1 reads grow, as the number of lists on the site grows.
**Evidence.** `src/data/34_lists-v2-bridge.js:302-304`:
`SELECT slug FROM lists WHERE owner_account_id = ? AND deleted_at IS NOT NULL AND deleted_at > ?`
inside `listsV2DashboardResponse` (the v2 `/api/creator/lists`, called from
`src/api/67_creator-api-routes.js:677`). Every index on
`lists.owner_account_id` is partial `WHERE deleted_at IS NULL`
(`schema.sql`: `idx_lists_owner_slug`, `idx_lists_owner`), so none can serve
`deleted_at IS NOT NULL`. Reproduced: yes, in the scratchpad (`scan.mjs`):
1,000 accounts, 10,000 lists, `ANALYZE` run: the plan is `SCAN lists`. The
same partial indexes make `DELETE FROM lists WHERE owner_account_id = ?`
(`34_:870`) and the foreign-key checks on `DELETE FROM accounts`
(`02_:1530`, plan `SCAN channels | SCAN lists`) scan too, but those run only
when an account is deleted.
**Root cause.** The deleted-lists lookup was added after the indexes, which
were written for live lists only.
**Fix.** A new migration (`0025`) with
`CREATE INDEX IF NOT EXISTS idx_lists_owner_deleted ON lists(owner_account_id, deleted_at) WHERE deleted_at IS NOT NULL;`,
the same line in `schema.sql` and its ledger seed, and a
`D1_SCHEMA_MANIFEST` entry ("Slower, not broken"). No code change.
**Test.** In `tests/migration-suite.test.mjs` (or the lists-v2 tests), assert
that `EXPLAIN QUERY PLAN` of that exact statement uses
`idx_lists_owner_deleted` and not `SCAN lists`. It fails without the index.
**Risk.** None for reads; one more index to maintain on list delete.

### DB-04 (Info, Database Schema, Confirmed): migrations 0022 and 0023 never record themselves in the ledger
**What a user would notice.** Nothing.
**Evidence.** `grep -c "INSERT OR IGNORE INTO schema_migrations" migrations/*.sql`
gives 0 for `0022_feedback_creator_name.sql` and `0023_media_app_sync.sql`
(1 for 0015-0021 and 0024), and `schema.sql`'s seed lists `'0021'` then
`'0024'`. `docs/OPERATIONS.md` §4 step 2 says every migration must end with
that line. Today nothing breaks: the gate reads only
`MAX(version)` (`readSchemaLedger`, `src/core/02_http-and-creator-utils.js:411`)
and `/admin` → Check schema looks for the objects themselves
(`D1_SCHEMA_MANIFEST` has 0022's column and index and 0023's table).
Someone following §4 step 2 ("SELECT version FROM schema_migrations") would
think 0022 and 0023 were never applied.
**Fix.** Add `('0022', 0), ('0023', 0)` to `schema.sql`'s seed. Applied
migration files are not edited; a note in `docs/OPERATIONS.md` §4 that these
two do not record themselves is enough for the live database.
**Test.** The drift test could also check that every file in `migrations/`
from 0014 on appears in `schema.sql`'s seed; it fails today.
**Risk.** None.

## Checked and fine
**Data Loss.**
- The duplicate-title merge (`mediaMergeMainStatements` /
  `mediaMergeActivityStatements`, `src/data/29_media.js:760-818`): plays move
  before the spare row is deleted, `UPDATE OR IGNORE` + `DELETE` keeps one
  list entry when a list has both, counts are added, not replaced, and the
  spare is deleted only `AND imdb_id IS NULL`.
- The list save (`planListEntryDiff`, `src/data/34_lists-v2-bridge.js:477`)
  deletes only entries missing from the desired list, inserts with
  `INSERT OR IGNORE`, and writes everything in one `batch`, so a half-finished
  request changes nothing.
- Account deletion (`src/jobs/51_account-purge.js`): tombstone first, a
  retried job, likes taken back from the totals, shared channels kept with no
  owner, private channels' R2 pools deleted under the same
  `channels/<code>/` prefix they are written to (`channelsV2PoolKey`,
  `src/data/35_channels-v2.js:48`). (`docs/ARCHITECTURE.md` still names the
  old `channel/{code}/pool.json.gz` path: a doc nit.)
- Presets and channels saves carry an `expectedUpdatedAt` conflict guard
  (`src/api/69_creator-api-sync-routes.js:52-66`, `:99-112`).

**Backup & Recovery.**
- The D1 dump handles virtual tables, long rows and blobs, and every kept
  file is decrypted, loaded and row-counted before upload. Restore steps are
  written (`docs/OPERATIONS.md` §5). Time Travel covers 30 days.
- No restore into a real D1 database was tested (see Not covered).

**Data Integrity.**
- Like totals move by `changes()` in the same batch as the like row
  (`likeWriteStatements`, `src/api/32_likes-api.js:126-145`), so a repeat or
  a race cannot move a count twice.
- `lists.item_count` is recomputed with `count(*)` in the save's batch
  (`34_:703`). `media.kind`, `lists.visibility`, `lists.media_type`,
  `show_progress.status` have CHECKs; `watch_events.dedupe_key` is UNIQUE;
  `accounts.username` is UNIQUE NOCASE and the code lower-cases names.

**Data Relationships.**
- `accounts.id` has no AUTOINCREMENT, so ids are reused; `deleteAccountRow`
  (`src/core/02_http-and-creator-utils.js:1485`) deletes the accounts row only
  after `purgeAccountRowsById` reports success, and that clears the activity
  database (no FK there, separate database), likes cast, recommendations,
  preferences, presets, private channels and jobs.
- Support threads are detached from a deleted username
  (`detachFeedbackThreadsFromCreator`, `src/admin/03_admin.js:382`), so a
  re-registered name cannot read them.
- `channels.owner_account_id ON DELETE SET NULL` matches the purge, which
  keeps shared channels ownerless.

**Database Schema / Migrations.**
- All migrations replayed in order on the legacy base used by
  `tests/migration-suite.test.mjs`, then compared with `schema.sql` by
  columns, defaults, NOT NULL, keys, foreign keys and index columns
  (scratchpad `mig2.mjs`): identical except column order in `creator_lists`
  and `creator_show_states` (added by ALTER; nothing inserts without column
  names into them). No migration drops or rewrites data; 0022 and 0024's
  ALTERs say they run once only. `D1_SCHEMA_MANIFEST` covers 0022-0024.

**Query Efficiency.**
- `EXPLAIN QUERY PLAN` over every `prepare(...)` string in `src/` (scratchpad
  `eqp.mjs`): 56 statements scan a table. Apart from DB-03 they are admin
  pages, daily or hourly jobs over small or per-day data (`rollup.daily`,
  `show.watchers`, `token.refresh`), account deletion, or queries on
  `accounts` by `lower(username)` (about 1,100 rows). The materializer's
  `imdb_id IN … OR tmdb_id IN …` (`54_:73`) uses both media indexes once
  statistics exist.

**Data Consistency.**
- A list is read from D1 `creator_lists` first, KV adding only source fields
  (`readLegacyCreatorList`, `src/data/30_lists-backfill.js:159`); the v2 copy
  is keyed by a hash of that record, so a stale copy is redone on the next
  save.

**Key-value and file storage.**
- Every `CONFIGS.put` without `expirationTtl` was listed: they are per-account
  keys (removed by `purgeCreatorData`'s key list,
  `src/core/02_http-and-creator-utils.js:4841`), cron cursors, fixed admin
