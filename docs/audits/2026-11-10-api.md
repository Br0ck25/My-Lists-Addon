## Findings

### API-01 (Medium, Incoming webhooks, Confirmed): one Plex/Jellyfin/Emby viewing is recorded as several plays, and starting or stopping early counts as watched
**What a user would notice.** Someone who watches one movie through Plex sees it
three or four times in Watch History (the activity-database history), and its
play count goes up by that much. Stopping a movie or episode after a few minutes
still marks it watched and moves Continue Watching on to the next episode.

**Evidence.** `src/api/64_media-server-scrobble.js:260`
`isPlayed = eventType === "media.scrobble" || eventType === "media.play" || eventType === "media.stop" || eventType === "media.resume";`
Jellyfin (line 321) treats every `playback*` event as a play
(`eventType.includes("playback")`, so PlaybackStart too) and Emby (line 345)
`playback.start` and `playback.stop`. Each counted event goes to
`recordActivityPlay` with `watchedAt` = the time the event arrived
(`recordScrobbleMoviePlay`, `watchedAt: Date.now()`), and
`activityPlayStatements` (`src/data/38_activity-scrobble.js`) only merges a play
with one of the same title **within ten minutes**
(`ACTIVITY_DEDUPE_WINDOW_MS = 10 * 60 * 1000`, `src/data/36_activity-db.js:89`).
A two-hour movie produces `media.play` at the start, `media.resume` after any
pause, `media.scrobble` at ~90% and `media.stop` at the end, each usually more
than ten minutes apart.

Reproduced: yes. Scratch test (real Worker through `tests/harness.mjs`, clock
stubbed) sending one viewing as Plex sends it:
`media.play` (0 min), `media.pause` (40), `media.resume` (60), `media.scrobble`
(120), `media.stop` (130). Result: 4 `watch_events` rows for the one title and
`user_media_state.watched_count = 4`. A second account sending only
`media.stop` at 10 minutes of 120 got `matched: "yes (Plex: Movie P)"` and one
play recorded. The legacy KV/D1 tracking record is not affected by the repeats
(`recordScrobbleMoviePlay` filters the title out before adding it again), but
the activity database is what Watch History pages (`watchHistoryPage`,
`src/data/39_activity-shelves.js:432`, one item per row) and what
`rollup.daily` counts for Most Watched (`rollupDay`, `src/jobs/53_more-jobs.js:254`).

**Root cause.** The webhook treats "something happened to this title" as "this
title was played", and the only guard against repeats is the ten-minute window
that was designed for a retried ping, not for the several events one viewing
sends over two hours.

**Fix.** Product choice first (see Questions for the owner): which events mean
"watched". Smallest safe change once decided:
1. In `detectMediaServerPayload`, count a play only on the finishing events:
   Plex `media.scrobble`; Jellyfin `PlaybackStop` with `PlayedToCompletion` /
   `Played === true` and `UserDataSaved` with `Played`; Emby `playback.stop`
   with `PlaybackInfo.PlayedToCompletion` and `item.markplayed`. Leave
   `media.play`/`resume`/`stop` to `recordPausedPosition`, which already stores
   where the person stopped.
2. If the owner wants start-of-play to count (as the Stremio subtitles ping
   does), keep it but give the webhook its own repeat rule: one play per
   title per account per few hours, e.g. by passing the event's own time window
   to `activityPlayStatements` rather than widening the shared ten-minute rule
   used by the other sources.

**Test.** In `tests/plex-webhook.test.mjs`: one viewing sent as
play/pause/resume/scrobble/stop with the clock moved between events must leave
exactly one `watch_events` row and `watched_count = 1`; a `media.stop` at 10% must
not add a play (if the owner picks option 1). Fails today with 4 rows.

**Risk.** Jellyfin and Emby payloads differ by plugin version; the test
fixtures must use the documented field names. Fewer plays changes Most Watched
totals (accepted, they were inflated).

### API-02 (Low, Incoming webhooks, High): the Ko-fi webhook reads a body of any size when the sender leaves out Content-Length
**What a user would notice.** Nothing normally. Someone could send very large
fake "donations" with no length header; each is read in full into memory
before the verification token is checked, which can crash the Worker instance
serving other people at the same time.

**Evidence.** `src/api/71_poster-and-support-routes.js` (`apiKofiWebhook`):
`if ((Number(request.headers.get("content-length")) || 0) > KOFI_WEBHOOK_BODY_MAX)`
then `(await request.formData()).get("data")`. A chunked request has no
`Content-Length`, so the check sees 0 and `formData()` buffers the whole body;
the `raw.length > KOFI_WEBHOOK_BODY_MAX` check runs only after that. The same
header-only check guards `/api/scrobble` (`SCROBBLE_MAX_BODY_BYTES`, line 23 of
`64_media-server-scrobble.js`), but there the body is read only after a valid
`?st=` token, so only the token owner could do it. Searched: no other size
guard on this path (`grep -n content-length src -r`). Reproduced: no (needs a
real Cloudflare edge; the code path is plain).

**Root cause.** The size limit trusts a header the sender controls.

The CSP report sink has the same pattern, also before any credential:
`handleCspReport` (`src/core/02_http-and-creator-utils.js:290`) checks the
declared `Content-Length`, then `await request.text()`.

**Fix.** No "read at most N bytes" helper exists yet (searched for
`getReader()` outside client code). Add one small helper in `02_` that reads
`request.body` up to `max + 1` bytes and stops; use it in `apiKofiWebhook`
(413 above `KOFI_WEBHOOK_BODY_MAX`, then parse the text with
`URLSearchParams`) and in `handleCspReport` (204 above
`CSP_REPORT_MAX_BYTES`). One root cause, one commit.

**Test.** A POST to `/api/kofi-webhook` with a `ReadableStream` body of
`KOFI_WEBHOOK_BODY_MAX * 2` bytes and no `Content-Length` gets 413. Fails today
(400 or 401 after reading it all).

**Risk.** Ko-fi's real deliveries are a few KB; none would be refused.

### API-03 (Low, API Contract, Confirmed): a title's detail page that failed to load is cached by the app for an hour
**What a user would notice.** If TMDB is slow or down when someone opens a
movie or show in Stremio/Nuvio (with "Use My Lists Addon metadata" on), the
detail page comes back empty, and an app that honours HTTP caching keeps
showing it empty for up to an hour after TMDB recovers.

**Evidence.** `src/api/70_stremio-routes.js:531`
`if (!meta) return jsonPublic({ meta: null });` and the `catch` at line 547
`return jsonPublic({ meta: null, error: safeErrorMessage(err) });`.
`jsonPublic` → `jsonCacheable` (`src/core/02_http-and-creator-utils.js:798`)
adds `Cache-Control: max-age=3600` unless the status is 4xx/5xx or the body has
`ok: false`; `{ meta: null }` has neither. The catalog route already does the
right thing for its failures (`{ metas: [], error }` with `CATALOG_NO_CACHE`,
line 451), and the channel branch does too when the link is unknown
(line 492). Reproduced: yes. Scratch test with every outside call failing (the
harness blocks the network): `GET /meta/movie/tt0111161.json` →
`200 {"meta":null}` with `cache-control: max-age=3600`.

**Root cause.** "Nothing found" and "could not ask" both return `{ meta: null }`
through the cacheable helper; only the second should be uncacheable, and the
catch path is always the second.

**Fix.** Pass `CATALOG_NO_CACHE` (already used in this file) as the headers on
the `meta: null` returns of `stremioMetaItem`: the `catch` blocks (lines 519,
547) and the `!meta` return (line 531, which is what a TMDB failure turns
into, since `fetchStandardItemMeta` returns null rather than throwing). Leave
the successful `{ meta }` caching as it is.

**Test.** In `tests/metadata-off.test.mjs` or a new meta test: with fetch
stubbed to fail, `/meta/movie/tt0111161.json` answers with a
`Cache-Control` that contains `no-store`. Fails today (`max-age=3600`).

**Risk.** Unknown ids are asked again instead of cached; they are cheap (the
TMDB lookup itself is cached in KV and memory with a stale fallback).

## Checked and fine
**Timeout Handling.** Every `fetch(` in the Worker resolves to the module-level
guard `fetch()` (`src/core/02_http-and-creator-utils.js:2946`), which adds a
30 s `AbortSignal.timeout` (`OUTBOUND_DEFAULT_TIMEOUT_MS`) to any call without
its own signal and routes provider hosts through the breaker. Catalog-path
calls use `fetchWithTimeout` (10 s). Calls that set their own signal all set a
timeout (`AbortSignal.timeout` in `28_connections.js`, `61_media-app-sync.js`
`mediaAppFetch`, `64_media-positions.js`, `61_nuvio-overview.js`; a timer +
`AbortController` in `fetchBetterPosterUpstream`). The only `fetch(req)` with a
Request object is the browser service worker (`25_`), which is the browser's
own navigation. `fetchTraktWithRetry` caps its wait at 3.5 s.

**API Contract.** Manifest (`buildManifest`, `05_catalog-core.js:9`): `id`,
`version`, `resources` (catalog, meta with `tt`/`tmdb:`/`channel_` prefixes,
subtitles only when tracking is on and not the TV Launcher), `types`,
`catalogs`; an unknown install link gets 404 with CORS and `no-store`.
Catalog route (`stremioCatalogRow`, `70_stremio-routes.js:190`): every
failure path answers `200 { metas: [] }` (with `error` and `no-store` when a
provider failed, or the last good copy marked `stale: true`), which is what
the apps need to show an empty row rather than an error; `skip`/`search`
extras are read from the path the way Stremio sends them. Subtitles ping
answers `{ subtitles: [] }` at once and records in `waitUntil`. All Stremio
routes go through `jsonPublic`, so CORS is on every one. Web API: failures
use `{ ok: false, error }`, which `json()` never caches; success is
`no-store` unless a route opts in (`jsonCacheable`).

**Compatibility.** `resolveConfig` (`04_config-resolution.js:104`) still
accepts every link form the apps hold: `/c/` prefix, `/tv/` variants,
`nuvio-default`, creator-sync links, `/i/{token}` (v2) and short legacy `cfg:`
ids (with secrets moved to `install_secrets` re-applied, revoked ones
answering an empty config). The bare `/manifest.json` and browser visits to a
manifest redirect to the configure page. The scrobble webhook's old
`?config=`/`?creator=&key=` forms answer 410 `sunset: true` by owner decision
(D-36), not a regression. The manifest still lists `meta` for `tmdb:` ids that
older Watch History entries carry.

**Incoming webhooks.** `/api/scrobble`: only `?st=` works; old forms get 410
before anything is checked (D-36); bad tokens spend an IP budget
(`reserveRateLimit`), a good token never does; tombstoned accounts refused;
JSON/multipart parse errors give 400; non-play events (pause) store only a
position. `/api/kofi-webhook`: token compared with `timingSafeEqualSecret`,
IP-limited (120/min), duplicates are refused by message id in the same D1
batch as the count, a failed settings read answers 503 so Ko-fi retries
instead of writing defaults. Inbound email (`email()` handler, `59_`): errors
are caught and logged; attachment size is capped
(`SUPPORT_ATTACHMENTS_MAX_CHARS`), and Cloudflare Email Routing caps the
message itself.
