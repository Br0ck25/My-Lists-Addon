## Findings

### API-01 (Medium, Incoming webhooks, Confirmed): one Plex/Jellyfin/Emby viewing is recorded as several plays, and starting or stopping early counts as watched
**What a user would notice.** Someone who watches one movie through Plex sees it
three or four times in Watch History (the activity-database history), and its
play count goes up by that much. Stopping a movie or episode after a few minutes
still marks it watched and moves Continue Watching on to the next episode.

**Evidence.** `src/api/64_media-server-scrobble.js:260`
`isPlayed = eventType === "media.scrobble" || eventType === "media.play" || eventType === "media.stop" || eventType === "media.resume";`
Jellyfin (line 321) treats every `playback*` event as a play
(`eventType.includes("playback")`, so PlaybackStart too) and Emby (line 345)
`playback.start` and `playback.stop`. Each counted event goes to
`recordActivityPlay` with `watchedAt` = the time the event arrived
(`recordScrobbleMoviePlay`, `watchedAt: Date.now()`), and
`activityPlayStatements` (`src/data/38_activity-scrobble.js`) only merges a play
with one of the same title **within ten minutes**
(`ACTIVITY_DEDUPE_WINDOW_MS = 10 * 60 * 1000`, `src/data/36_activity-db.js:89`).
A two-hour movie produces `media.play` at the start, `media.resume` after any
pause, `media.scrobble` at ~90% and `media.stop` at the end, each usually more
than ten minutes apart.

Reproduced: yes. Scratch test (real Worker through `tests/harness.mjs`, clock
stubbed) sending one viewing as Plex sends it:
`media.play` (0 min), `media.pause` (40), `media.resume` (60), `media.scrobble`
(120), `media.stop` (130). Result: 4 `watch_events` rows for the one title and
`user_media_state.watched_count = 4`. A second account sending only
`media.stop` at 10 minutes of 120 got `matched: "yes (Plex: Movie P)"` and one
play recorded. Re-run with `FF_EVENT_TRACKING: "1"` (on in production since
Release 11): same result, `watched_count = 4`. The legacy KV/D1 tracking record is not affected by the repeats
(`recordScrobbleMoviePlay` filters the title out before adding it again), but
the activity database is what Watch History pages (`watchHistoryPage`,
`src/data/39_activity-shelves.js:432`, one item per row) and what
`rollup.daily` counts for Most Watched (`rollupDay`, `src/jobs/53_more-jobs.js:254`).

**Root cause.** The webhook treats "something happened to this title" as "this
title was played", and the only guard against repeats is the ten-minute window
that was designed for a retried ping, not for the several events one viewing
sends over two hours.

**Fix.** Owner decided (2026-11-10): **a title counts as watched only when
it is finished (about 90%)**; stopping early only saves the place. Steps:
1. In `detectMediaServerPayload`, set `isPlayed` only on the finishing
   events: Plex `media.scrobble`; Jellyfin `PlaybackStop` with
   `PlayedToCompletion === true`, or any event with `Played === true`
   (`UserDataSaved` after "mark played"); Emby `playback.stop` with
   `PlaybackInfo.PlayedToCompletion === true`, and `item.markplayed`.
   `media.play`, `media.resume`, `PlaybackStart`/`PlaybackProgress` and
   `playback.start` no longer count.
2. Keep saving the place for an early stop. Today the not-played branch in
   `handleMediaServerScrobbleFor` calls `recordPausedPosition` only for
   `media.pause`; widen it to the stop events too (Plex `media.stop`,
   Jellyfin `PlaybackStop`, Emby `playback.stop`) so a stop at 50% still
   lands in `watch_positions`, as it does today through
   `recordScrobblePosition`.
3. A Plex viewing still sends `media.scrobble` once and then `media.stop`
   minutes later; the stop is no longer a play, so one viewing is one row.
   Do not change the shared ten-minute rule (`ACTIVITY_DEDUPE_WINDOW_MS`),
   which the Stremio/Nuvio ping relies on.

**Test.** In `tests/plex-webhook.test.mjs` (and a Jellyfin and an Emby case
using their documented field names): one viewing sent as
play/pause/resume/scrobble/stop with the clock moved between events leaves
exactly one `watch_events` row and `watched_count = 1`; a lone `media.stop`
at 10 minutes of 120 adds no play and does store a position (10 min / 120
min) in `watch_positions`; a Jellyfin `PlaybackStop` with
`PlayedToCompletion: true` adds one play. Fails today with 4 rows and a play
for the early stop. Update `tests/playback-positions.test.mjs` only where it
assumed a stop is a play (it should not need to: positions are still
stored).

**Risk.** Jellyfin and Emby payloads differ by plugin version; the test
fixtures must use the documented field names. Fewer plays changes Most Watched
totals (accepted, they were inflated).

### API-02 (Low, Incoming webhooks, High): the Ko-fi webhook reads a body of any size when the sender leaves out Content-Length
**What a user would notice.** Nothing normally. Someone could send very large
fake "donations" with no length header; each is read in full into memory
before the verification token is checked, which can crash the Worker instance
serving other people at the same time.

**Evidence.** `src/api/71_poster-and-support-routes.js` (`apiKofiWebhook`):
`if ((Number(request.headers.get("content-length")) || 0) > KOFI_WEBHOOK_BODY_MAX)`
then `(await request.formData()).get("data")`. A chunked request has no
`Content-Length`, so the check sees 0 and `formData()` buffers the whole body;
the `raw.length > KOFI_WEBHOOK_BODY_MAX` check runs only after that. The same
header-only check guards `/api/scrobble` (`SCROBBLE_MAX_BODY_BYTES`, line 23 of
`64_media-server-scrobble.js`), but there the body is read only after a valid
`?st=` token, so only the token owner could do it. Searched: no other size
guard on this path (`grep -n content-length src -r`). Reproduced: no (needs a
real Cloudflare edge; the code path is plain).

**Root cause.** The size limit trusts a header the sender controls.

The CSP report sink has the same pattern, also before any credential:
`handleCspReport` (`src/core/02_http-and-creator-utils.js:290`) checks the
declared `Content-Length`, then `await request.text()`.

**Fix.** No "read at most N bytes" helper exists yet (searched for
`getReader()` outside client code). Add one small helper in `02_` that reads
`request.body` up to `max + 1` bytes and stops; use it in `apiKofiWebhook`
(413 above `KOFI_WEBHOOK_BODY_MAX`, then parse the text with
`URLSearchParams`) and in `handleCspReport` (204 above
`CSP_REPORT_MAX_BYTES`). One root cause, one commit.

**Test.** A POST to `/api/kofi-webhook` with a `ReadableStream` body of
`KOFI_WEBHOOK_BODY_MAX * 2` bytes and no `Content-Length` gets 413. Fails today
(400 or 401 after reading it all).

**Risk.** Ko-fi's real deliveries are a few KB; none would be refused.

### API-03 (Low, API Contract, Confirmed): a title's detail page that failed to load is cached by the app for an hour
**What a user would notice.** If TMDB is slow or down when someone opens a
movie or show in Stremio/Nuvio (with "Use My Lists Addon metadata" on), the
detail page comes back empty, and an app that honours HTTP caching keeps
showing it empty for up to an hour after TMDB recovers.

**Evidence.** `src/api/70_stremio-routes.js:531`
`if (!meta) return jsonPublic({ meta: null });` and the `catch` at line 547
`return jsonPublic({ meta: null, error: safeErrorMessage(err) });`.
`jsonPublic` → `jsonCacheable` (`src/core/02_http-and-creator-utils.js:798`)
adds `Cache-Control: max-age=3600` unless the status is 4xx/5xx or the body has
`ok: false`; `{ meta: null }` has neither. The catalog route already does the
right thing for its failures (`{ metas: [], error }` with `CATALOG_NO_CACHE`,
line 451), and the channel branch does too when the link is unknown
(line 492). Reproduced: yes. Scratch test with every outside call failing (the
harness blocks the network): `GET /meta/movie/tt0111161.json` →
`200 {"meta":null}` with `cache-control: max-age=3600`.

**Root cause.** "Nothing found" and "could not ask" both return `{ meta: null }`
through the cacheable helper; only the second should be uncacheable, and the
catch path is always the second.

**Fix.** Pass `CATALOG_NO_CACHE` (already used in this file) as the headers on
the `meta: null` returns of `stremioMetaItem`: the `catch` blocks (lines 519,
547) and the `!meta` return (line 531, which is what a TMDB failure turns
into, since `fetchStandardItemMeta` returns null rather than throwing). Leave
the successful `{ meta }` caching as it is.

**Test.** In `tests/metadata-off.test.mjs` or a new meta test: with fetch
stubbed to fail, `/meta/movie/tt0111161.json` answers with a
`Cache-Control` that contains `no-store`. Fails today (`max-age=3600`).

**Risk.** Unknown ids are asked again instead of cached; they are cheap (the
TMDB lookup itself is cached in KV and memory with a stale fallback).

### API-04 (Medium, Data Mapping / Integration Reliability, Confirmed): a Stremio pull silently skips the watched episodes of shows past the 30th in each batch, or of every show when Cinemeta is down, and never comes back for them
**What a user would notice.** Someone who connects a Stremio account with many
shows finds that only some of their shows came across with the episodes they
had watched; the rest are missing from Continue Watching / show progress. The
settings page says the sync worked, and pressing Sync again does not bring
them in, because the sync now only looks at titles that changed in Stremio
since then.

**Evidence.** `src/api/61_media-app-sync.js:68-69`
`const MEDIA_APP_STEP_ITEMS = 120;` `const MEDIA_APP_CINEMETA_PER_STEP = 30;`
and in `mediaAppFetchRecords` (line 756):
`if (hasBits && cinemeta > 0) { cinemeta--; episodes = await stremioEpisodes(String(item._id)); }`.
A show past the 30th in a slice of 120 gets `episodes = null`, and
`stremioItemRecord` then reads no watched episodes
(`const watchedEps = episodes && st.watched ? ... : []`). `stremioEpisodes`
also returns `null` on any Cinemeta failure (`if (!res.ok) return null;`,
`catch { return null; }`), with the same result. Nothing marks those items as
"not done": `pullMediaAppStep` (line 858) saves
`mtime: Math.max(cursor.mtime, fetched.newest)` and clears `last_error`, and
the next pull reads only items with `_mtime >= cursor.mtime - 5 min`
(`MEDIA_APP_OVERLAP_MS`).

Reproduced: yes. Scratch test through the real Worker with Stremio and
Cinemeta faked the way `tests/media-app-sync.test.mjs` fakes them:
- 40 shows, each with E1–E4 marked watched in the bitfield: after the pull,
  `cinemetaCalls=30`, `show_progress` rows = 30, `last_error` = null, cursor
  `mtime` at the newest item. 10 shows imported nothing.
- 3 shows with Cinemeta answering 503: `show_progress` rows = 0,
  `last_error` = null, cursor advanced.

**Root cause.** The per-step Cinemeta budget and a Cinemeta failure both turn
into "this show has no watched episodes" instead of "this show is not read
yet", and the pull's "changed since" mark moves past it either way.

**Fix.** Smallest change, in `mediaAppFetchRecords` and `pullMediaAppStep`:
1. When a show needs Cinemeta (`hasBits`) and the budget is spent, end the
   step's slice at that item (return the records so far and let `offset`
   move on by the number actually read, not by `MEDIA_APP_STEP_ITEMS`), so
   the next step starts with it. The job already runs in bounded steps.
2. When `stremioEpisodes` returns null for a show with bits, throw a
   `mediaAppError("unreachable", "Cinemeta could not be reached.")` so the
   job retries later (`pullMediaAppStep` already turns that into a shown
   error and a job retry) and the cursor is not moved.
Distinguish "Cinemeta has no such show" (404, keep today's behaviour) from
"Cinemeta failed" (5xx, timeout) in `stremioEpisodes` by returning a marker
or throwing for the second.

**Test.** In `tests/media-app-sync.test.mjs`: a library of 40 shows with
watched bits ends with 40 `show_progress` rows after the pull ticks; with
Cinemeta answering 503 the pull leaves `last_error` set and the cursor
`mtime` unchanged, and once Cinemeta answers again a later pull imports the
shows. Both fail today (30 rows; null error and an advanced cursor).

**Risk.** Smaller steps mean more job runs for a large library (each still
bounded). A show Cinemeta does not list must not block the pull forever:
keep 404 as "no episodes".

### API-05 (Medium, Rate Limiting, Confirmed): one person's over-quota MDBList, Trakt or TMDB key switches that provider off for everyone for a minute at a time
**What a user would notice.** When one user's own MDBList (or Trakt, or
personal TMDB) key runs out of its daily allowance, everyone else's rows from
that provider stop updating for a minute: they get the last saved copy, or an
empty row if there is none. While that one person keeps opening Stremio, it
keeps happening.

**Evidence.** `src/catalog/41_provider-breaker.js:124`
`return !status || status >= 500 || status === 429;` counts a 429 as the
provider being down, and the count is per provider, not per key
(`PROVIDER_BREAKERS` keyed by provider id, `providerForHost` maps every
`api.mdblist.com` call to `"mdblist"`). After `PROVIDER_BREAKER_THRESHOLD = 5`
in a row the breaker opens for 60 s, and `providerBreakerFlush` publishes it
to KV (`pb:mdblist`) so every isolate takes it up within a minute
(`providerBreakerRefresh`). MDBList and Trakt limits are per API key / per
user token, so a 429 there is about that caller, like the 401/403 the
breaker already ignores. `FF_PROVIDER_BREAKER` is on in production
(`docs/RELEASES.md:20`, Release 13).

Reproduced: yes. Scratch script loading the built Worker with the guard
exported, breaker on, `fetch` stubbed so `apikey=EXHAUSTED` gets 429 and any
other key 200: five calls with the exhausted key (429 each), then one call
with a good key → refused with `ProviderUnavailable: MDBList is not answering
right now`, without being sent.

**Root cause.** The breaker treats "this key is over its limit" the same as
"the provider is down", and shares that across all users.

**Fix.** In `isProviderFailureStatus` (or in `providerBreakerRecord`), stop
counting 429 for providers whose limits are per caller: MDBList, Trakt,
Simkl, and TMDB when the call carries a personal key. The simplest safe
version: count 429 only for providers called with the site's own key
(TMDB with the shared key, RapidAPI, JustWatch, TVmaze, Cinemeta), and treat
429 as an answer (resets the count, like 401/403) for the others. The cache
tiers already serve the stale copy on a 429 for that one caller
(`fetchWithPerUserCacheAndCircuitBreaker`, `02_`), so that user loses
nothing.

**Test.** In `tests/providers.test.mjs` (already sets `FF_PROVIDER_BREAKER`):
five 429 answers for one MDBList key, then a call with another key reaches
the stub and gets its 200. Fails today (refused). Keep the existing test that
five 5xx answers still open the breaker.

**Risk.** If MDBList as a whole started answering 429 to everyone, the
breaker would no longer stop calling it; each call still has its timeout and
stale fallback, so rows still load, only slower.

## Checked and fine
**Timeout Handling.** Every `fetch(` in the Worker resolves to the module-level
guard `fetch()` (`src/core/02_http-and-creator-utils.js:2946`), which adds a
30 s `AbortSignal.timeout` (`OUTBOUND_DEFAULT_TIMEOUT_MS`) to any call without
its own signal and routes provider hosts through the breaker. Catalog-path
calls use `fetchWithTimeout` (10 s). Calls that set their own signal all set a
timeout (`AbortSignal.timeout` in `28_connections.js`, `61_media-app-sync.js`
`mediaAppFetch`, `64_media-positions.js`, `61_nuvio-overview.js`; a timer +
`AbortController` in `fetchBetterPosterUpstream`). The only `fetch(req)` with a
Request object is the browser service worker (`25_`), which is the browser's
own navigation. `fetchTraktWithRetry` caps its wait at 3.5 s.

**API Contract.** Manifest (`buildManifest`, `05_catalog-core.js:9`): `id`,
`version`, `resources` (catalog, meta with `tt`/`tmdb:`/`channel_` prefixes,
subtitles only when tracking is on and not the TV Launcher), `types`,
`catalogs`; an unknown install link gets 404 with CORS and `no-store`.
Catalog route (`stremioCatalogRow`, `70_stremio-routes.js:190`): every
failure path answers `200 { metas: [] }` (with `error` and `no-store` when a
provider failed, or the last good copy marked `stale: true`), which is what
the apps need to show an empty row rather than an error; `skip`/`search`
extras are read from the path the way Stremio sends them. Subtitles ping
answers `{ subtitles: [] }` at once and records in `waitUntil`. All Stremio
routes go through `jsonPublic`, so CORS is on every one. Web API: failures
use `{ ok: false, error }`, which `json()` never caches; success is
`no-store` unless a route opts in (`jsonCacheable`).

**Compatibility.** `resolveConfig` (`04_config-resolution.js:104`) still
accepts every link form the apps hold: `/c/` prefix, `/tv/` variants,
`nuvio-default`, creator-sync links, `/i/{token}` (v2) and short legacy `cfg:`
ids (with secrets moved to `install_secrets` re-applied, revoked ones
answering an empty config). The bare `/manifest.json` and browser visits to a
manifest redirect to the configure page. The scrobble webhook's old
`?config=`/`?creator=&key=` forms answer 410 `sunset: true` by owner decision
(D-36), not a regression. The manifest still lists `meta` for `tmdb:` ids that
older Watch History entries carry.

**Data Mapping.** Stremio library items (`stremioItemRecord`): `_id` must be
`tt…` or `tmdb:N` (`mediaAppTitleId`), shows need an IMDb id, times accept
ISO, seconds or milliseconds (`mediaAppTime`), the watched bitfield is
re-anchored when a show gains episodes (covered by
`tests/media-app-sync.test.mjs`). Nuvio rows (`nuvioRecords`): TMDB ids are
keyed by kind so movie 550 and show 550 never merge; an explicit "movie"
wins over stray season/episode numbers; a resume point behind the furthest
watched episode is dropped. Plex episodes take the show from
`grandparentGuid` and find it through the episode's own ids via TMDB `/find`
(`resolveScrobbleIds`), so an episode id is never stored as the show.
Subtitles ping ids (`tt…:S:E`, `tmdb:N:S:E`, `kitsu:N:E`) are split as Stremio
sends them.

**Integration Reliability.** Stremio (`stremioCall`) and Nuvio (`nuvioRpc`,
`nuvioToken`) answers that are not JSON, not an object, missing `result`, or
the wrong shape throw a typed error ("invalid" → reconnect needed,
"unreachable" → job retries, message shown on the settings page); Nuvio's
paginated reads refuse to save a partial or repeated page. TMDB/Trakt/MDBList
catalog reads fall back to memory → KV → edge cache → stale copy
(`fetchWithPerUserCacheAndCircuitBreaker`), with the provider breaker
(`41_provider-breaker.js`) refusing fast while a provider is down. Better
Poster and RPDB fetches fail to the plain poster.

**Incoming webhooks.** `/api/scrobble`: only `?st=` works; old forms get 410
before anything is checked (D-36); bad tokens spend an IP budget
(`reserveRateLimit`), a good token never does; tombstoned accounts refused;
JSON/multipart parse errors give 400; non-play events (pause) store only a
position. `/api/kofi-webhook`: token compared with `timingSafeEqualSecret`,
IP-limited (120/min), duplicates are refused by message id in the same D1
batch as the count, a failed settings read answers 503 so Ko-fi retries
instead of writing defaults. Inbound email (`email()` handler, `59_`): errors
are caught and logged; attachment size is capped
(`SUPPORT_ATTACHMENTS_MAX_CHARS`), and Cloudflare Email Routing caps the
message itself.

**Retry Logic.** Outbound retries happen only on 429 (Trakt
`fetchTraktWithRetry`: 2 retries, Retry-After honoured up to 3 s plus jitter;
Stremio `stremioCall` and Nuvio `nuvioRpc`: 3 retries, Retry-After or
0.4/0.8/1.6 s, capped at 3 s). A 429 means the request was not processed, so
re-sending a write (Stremio `datastorePut`, Nuvio RPCs) cannot double it. No
outbound call is retried on 5xx or timeout inside a request. Background jobs
retry through the queue with growing delays (`jobRetryDelaySec`, `44_`), then
go to the dead-letter queue after `JOBS_MAX_RETRIES`; a job can ask to be
re-delivered later without it counting as a failure (`retryAfterSeconds`).
The other `for (let attempt …)` loops are local compare-and-swap retries on
our own storage (likes, slugs, tracking record), not outbound calls. Ko-fi
redeliveries are de-duplicated by message id (Incoming webhooks).

**Rate Limiting.** Our own limits are D1 counters (D-28/D-29/D-30): signup,
sign-in, search catalog (`searchRateLimitResponse`, so one client cannot burn
the shared TMDB key), bad scrobble tokens, Ko-fi, CSP reports. Staying inside
providers' limits: TMDB/Trakt/MDBList reads are cached in memory, KV and the
edge with a stale copy on 429 (`fetchWithPerUserCacheAndCircuitBreaker`,
`02_:2627`); RPDB backs off on 429 (`RPDB_BACKOFF_SECONDS`); Trakt and
MDBList 429s show "busy, try again" rather than an empty list
(`06_source-fetchers-mdblist-trakt.js:588`, `:1151`); the Stremio pull reads
Cinemeta at most 30 times a step (but see API-04).

## Unverified hunches
- **Jellyfin and Emby episodes may be stored under the episode's own id
  instead of the show's.** `detectMediaServerPayload`
  (`src/api/64_media-server-scrobble.js:338-339`, `:362-363`) falls back from
  `SeriesProviderIds` to the item's own `ProviderIds` / `Provider_imdb` /
  `Provider_tmdb`. If the Jellyfin webhook plugin's default template and
  Emby's webhook send only the episode's ids for an episode (the same thing
  the Plex comment in that function describes fixing for Plex), the play is
  saved with `showId` = the episode's IMDb id, and a `Provider_tmdb` (the
  episode's TMDB id) would be used as the show's TMDB id for the season
  lookup. There is no Jellyfin or Emby episode fixture in `tests/` (`grep -n
  SeriesName tests/*.mjs` finds nothing). To confirm: capture one real
  episode payload from each server (owner step below) and check which ids it
  carries.
- **`tmdb:<id>:<n>` subtitles pings read the TMDB id as the season.**
  `src/api/63_subtitles-track.js:110-111`: with two parts after `tmdb:`,
  `season = Number(tmdbParts[0])` (the show id). The `kitsu:` and plain
  branches use season 1 for the same shape. Not known whether any app sends
  a two-part `tmdb:` id; the usual form has three parts and is read
  correctly.
- **A series detail page can be cached for a day with seasons missing.**
  `fetchStandardItemMeta` (`07_source-fetchers-tmdb-simkl.js:4418`) turns a
  failed season into `null` (`.catch(() => null)`) and the meta route caches
  the result `public, max-age=86400`. Each season read has its own stale
  fallback, so this needs a season never read before plus a TMDB failure; a
  scratch reproduction did not get far enough (the stubbed show lookup
  returned no meta) to show it.
