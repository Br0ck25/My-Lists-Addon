## Findings
### UI-01 (Medium, Error States, Confirmed): error messages open behind the form that caused them
**What a user would notice.** In Create List (and seven other pop-up forms), if the server refuses the save, nothing seems to happen: the form stays open and the "Could Not Save List" message is hidden behind it. Only after pressing Cancel does the message appear.
**Evidence.** `src/page/09_page-shell.js:5389` `<div id="createListModal" class="modal-overlay …" style="display:none; z-index:10001; …">`; the same inline `z-index:10001` is on `createCollectionModal`, `importNuvioCollectionsModal`, `syncNuvioModal`, `addShelfModal`, `importListModal`, `importChannelModal`, `selectListModal` (`grep -n 'z-index:10001' src/page/09_page-shell.js`, 8 hits). The message comes from `showModal()` (`src/client/16_client-row-core.js:2298`), whose `.modal-overlay` uses `z-index: var(--z-modal)` = 1000 (`src/page/09_page-shell.js:4677`, token at `src/core/00_constants.js:1858`). `src/client/22_client-creator-profile.js:6250` calls `showAppNoticeModal('Could Not Save List', …)` while `createListModal` is still open. Reproduced in Playwright: signed in, POSTs answered with 500 `{"ok":false,"error":"Server exploded"}`, Create List → Create. `document.elementsFromPoint` at the centre of the screen lists `#createListModal` (z 10001) above `#activeModalOverlay` (z 1000) holding "Could Not Save List / Server exploded / OK". No toast. Focus also moves into the hidden dialog (`showModal` focuses its heading), so a keyboard user is lost.
**Root cause.** The eight static forms were given a hard-coded `z-index:10001`, above the `--z-modal` layer every `showModal`/`appShellDialog`/`showAppNoticeModal` dialog uses, so any dialog opened from inside them stacks underneath.
**Fix.** Remove the inline `z-index:10001` from the eight static modals so they use `--z-modal` like every other dialog (later-appended `#activeModalOverlay` then sits on top by document order), or add one `--z-modal-raised` token for `#activeModalOverlay` if order is not enough. Do not add a new number.
**Test.** Client/Playwright test: open `createListModal`, call `showAppNoticeModal('x','y',true)`, assert `document.elementFromPoint(centre)` is inside `#activeModalOverlay`. Fails today. A guard in `tests/design-system.test.mjs` that no `z-index:` numeric literal appears in page HTML would also catch a repeat.
**Risk.** Check the mobile bottom nav (`--z-nav` 900) still sits below the forms, and that the forms still cover the sticky header.

### UI-02 (Low, Error States, Confirmed): a saved sub-tab name the page no longer knows leaves Discover, Catalogs or Channels blank
**What a user would notice.** The Discover page shows an empty white card under the filter pills (with "All" ticked) and no lists; Catalogs and Channels show an empty panel. Reloading does not help, because the bad value is remembered.
**Evidence.** `src/client/16_client-row-core.js:201`, `:241`, `:287` read `myListAddon:catalogsSubmenu`, `channelsSubmenu` and `discoverSubmenu` straight from storage (`|| 'movie'` only covers a missing value); only Lists has a whitelist (`normalizeListsSubmenu`, `:184`). Same pattern in `src/page/09_page-shell.js:265-279`. Reproduced: every `myListAddon:*` key set to `123` → `/`, `/catalogs`, `/channels` render under 300 characters of text; bisected to one key, `myListAddon:discoverSubmenu`; `discoverSubmenu="trending"` gives the blank Discover page (screenshot taken). Other keys with junk values (`{not json`, `null`, `{}`) caused no page errors.
**Root cause.** Saved sub-tab names are trusted. A name renamed or dropped in a later release (the reason `normalizeListsSubmenu` exists) or written by another version of the page in the same browser turns into a panel that matches nothing.
**Fix.** Add a small `normalizeSubmenu(tab, raw)` beside `normalizeListsSubmenu` with each tab's known names (from the pills) and use it at every read listed by `grep -n "Submenu')" src/client src/page`.
**Test.** Client test: set `discoverSubmenu` to `"trending"`, load, assert the Movies pill is active and the Discover shelves render.
**Risk.** Low. Keep `build` (channels) and `keys` (settings), which are valid without a pill.

### UI-03 (Low, Error States, Confirmed): a server error on Catalogs is reported as a "network error", with no way to retry
**What a user would notice.** When the site has a hiccup, each catalog in My Catalogs says "Network error loading this catalog." even though their own connection is fine, and there is no Retry button; Discover shows a Retry button for the same failure.
**Evidence.** `src/client/23_client-list-management.js:1398` `'… Network error loading this catalog.</p>'` in the `catch` that also catches `res.json()` failing on a non-JSON 502/500. Reproduced: `/api/preview` answered with an HTML 502 → that text on every catalog; Discover shows "Couldn't load previews for this list. [Retry]" (`retryPosterSlot`, `src/client/19_client-search-and-likes.js:1438`). The text also breaks the "Could not …" copy rule.
**Root cause.** The catch treats any exception as a network failure, and the Catalogs preview never got the retry button the Discover cards have.
**Fix.** Word it "Could not load this catalog." and add the same `lc-btn` Retry that re-runs this one preview (the existing per-row refresh).
**Test.** Client test with `fetch` resolving to a non-JSON 502: assert the text starts "Could not" and a `[data-act]` Retry button is present.
**Risk.** Low.


### UI-04 (Low, State Management, Confirmed): reloading the channel builder throws away the half-built channel, and reopens an empty builder even after signing out
**What a user would notice.** Someone half-way through building a channel who reloads, or whose phone reloads the tab, comes back to an empty "Create a Custom Channel" form with no warning that their picks were lost. After signing out, the Channels tab still opens on that empty builder (with "My Channels" ticked), and they only learn they need an account when they press save.
**Evidence.** `src/client/20_client-channel-builder.js:10107` stores `localStorage.setItem('myListAddon:channelsSubmenu', name)` with `name === 'build'` (from `openBuildCustomChannel`, `:10149`); the early restore (`src/client/16_client-row-core.js:241-262`) shows `#channelsSubBuild` for that value. The draft (`channelDraftItems`, `#channelNameInput`) is memory only, and `grep -rn beforeunload src` finds nothing. Reproduced: signed in → Channels → + Create Channel → typed a name → reload: builder visible, name empty. Then signed out → `/channels`: `channelsSubmenu` still `build`, builder still visible. Saving is still guarded (`requireSignedInFor('build channels')`, `:10127` and others), so nothing wrong is saved.
**Root cause.** The builder is remembered as a sub-tab, but its draft is not, and nothing checks the sign-in state when restoring it.
**Fix.** Do not persist `build` as the remembered sub-tab (restore to `my-channels`), or restore it only when signed in and the draft is non-empty. Optionally warn on `beforeunload` while `channelDraftItems.length` is non-zero. Which of these is wanted is a product choice (see Questions).
**Test.** Client test: set `channelsSubmenu` to `build` with no creator key, load, assert `#channelsSubMyChannels` is shown and `#channelsSubBuild` hidden.
**Risk.** Low; the `?sub=build` deep link from the share flow should keep working.

### UI-05 (Low, State Management, Confirmed): signing out in one tab leaves other open tabs looking signed in
**What a user would notice.** With the site open in two tabs, signing out in one leaves the other showing their avatar ("Account: name"). Pressing "+ Create List" there then says "Sign in to create custom lists", which contradicts the avatar. New lists created in one tab also do not appear in the other until it is reloaded.
**Evidence.** `grep -n "'storage'" -r src/client src/page` finds no `storage` event listener. Reproduced in Playwright with two pages in one context: after sign-out in page 1, page 2's `#headerProfileBtn` keeps `aria-label="Account: aud37275"`; clicking `openCreateListModal` shows the sign-in dialog (screenshot taken). A list created in page 1 was not visible in page 2 after 2.5 s.
**Root cause.** The page reads the account from `localStorage` when it acts, but only paints the header on load, and never listens for another tab changing it.
**Fix.** One `window.addEventListener('storage', …)` that, when `myListAddon:creatorKey` changes, re-runs the existing header/profile refresh (or simply reloads the page when the key is removed).
**Test.** Client test: dispatch a `StorageEvent` for `myListAddon:creatorKey` with `newValue: null`, assert the header shows the signed-out button.
**Risk.** Avoid a reload loop if both tabs write the key at once; only react to removal or a different account name.

### UI-06 (Medium, Navigation, Confirmed): a dead shared-channel link shows a made-up channel credited to "My Lists Addon", and "+ Add" adds it
**What a user would notice.** Someone opens a shared channel link whose channel was deleted, renamed or mistyped (`/channels/<user>/<name>`). Instead of "this channel no longer exists" they see a channel called after the first part of the address (for example "Someone"), "by My Lists Addon • Shows • 0 items", "No items found." Pressing "+ Add" says `Added "Someone" to your Catalogs.` and puts an empty row into their add-on.
**Evidence.** Server: `src/api/73_public-list-routes.js:229-230` falls through to `renderPageCached(…)` with status 200 when no share code is found. Client: `src/client/24_client-backup-restore-presets.js:2505` `path.match('^/channels/([a-z0-9_-]+)')` takes only the first segment, and with no local match builds `chName = deslugify(slug)` and `chUrl = 'channel:v1:' + slug` (`:2519-2520`). Reproduced: `/channels/someone/deleted-channel` → page text "Someone / by My Lists Addon • Shows • 0 items / No items found."; clicking `button.list-add-btn` → toast `Added "Someone" to your Catalogs.` Same for `/channels/no-such-channel-xyz`.
**Root cause.** The channel deep link treats any address as a channel and invents a name and a `channel:v1:` source from the address, instead of saying the share was not found.
**Fix.** In `publishedChannelPage`, when a two-part address (`/channels/<user>/<slug>`) has no code, render the page with a "not found" deep-link flag (as `deepLinkList` is passed for charts), and have the client show an empty state ("Could not find this channel. It may have been removed.") with no "+ Add". Keep the one-segment storyline/network links working.
**Test.** Worker test: `GET /channels/nobody/nothing` must not lead to an addable row; client test: with the not-found flag, no `.list-add-btn` is rendered.
**Risk.** One-segment links (`/channels/tlc`) are used for network channels; do not break those.

### UI-07 (Low, Navigation, Confirmed): broken or old links are dead ends: endless "Loading…", raw JSON, or a bare "Not found"
**What a user would notice.** Three kinds of bad link each strand the visitor: `/lists/<anything unknown>` shows "List Title" and "Loading…" forever under a "Discover" heading; a shared list that was deleted or made private (`/lists/<user>/<list>`) shows the raw text `{"ok":false,"error":"No list found at that address."}`; any other unknown address (for example `/Lists`, `/settings/keys`, `/foo`) is a plain white page saying "Not found" with no link back to the site.
**Evidence.** `src/page/09_page-shell.js:233` `isDeep = (p.startsWith('/lists/') && p !== '/lists') || …` opens the list-details view for every `/lists/…` path, but `handleInitialDeepLink` (`src/client/24_client-backup-restore-presets.js:2364-2520`) has no branch for an unknown one-segment slug, so the "Loading…" placeholders are never replaced; the server comment at `src/api/73_public-list-routes.js:19-27` says an unknown slug should "just land on the normal default builder page". `src/api/73_public-list-routes.js:715` and `:745` return `json({ ok:false, error:"No list found at that address." }, 404)` for the browser address too. Plain 404: `curl -sI http://127.0.0.1:8787/foo` → `404`, `content-type: text/plain`, body `Not found`. All reproduced in Playwright (10 s wait for the Loading case).
**Root cause.** The page decides "this is a list link" from the path alone, and the Worker's not-found answers were written for feeds, not for people.
**Fix.** (1) In `handleInitialDeepLink`, when no branch matched, leave list-details and show the Discover tab (or a "Could not find this list." empty state). (2) For `/lists/<user>/<slug>` without `.json` and with an HTML `Accept`, return the page with a not-found message (status 404) instead of JSON. (3) Give the catch-all 404 a small HTML page with a link to `/`, keeping JSON for `/api/*`.
**Test.** Playwright/e2e: `/lists/bogus` shows no "Loading…" after load; Worker test: `GET /lists/x/y` with `Accept: text/html` returns `text/html`; `GET /foo` with `Accept: text/html` returns HTML containing a link to `/`.
**Risk.** Stremio/Nuvio fetch `/lists/<user>/<slug>.json`; keep JSON for `.json` and for `Accept: application/json`.

### UI-08 (Low, Loading States, Confirmed): "Generate Install Link" can be pressed twice and makes two install links
**What a user would notice.** On a slow connection the button stays clickable while "Generating install link…" shows below it. A second press makes a second, different install link; whichever answer comes back last is the one shown.
**Evidence.** `src/client/24_client-backup-restore-presets.js:1954-1990`: `generate()` writes a spinner into `#result` but never disables the `[data-act="generate"]` button or ignores a call already running. **Fix.** Reuse the existing helper in `src/client/17_client-skip-while-busy.js` (or the pattern Create list uses: `btn.disabled = true`, restore in `finally`) so a second call returns while the first runs.
**Test.** Client test: call `generate()` twice without awaiting, with `fetch` pending; assert one `/api/save` call.
**Risk.** The "Try again" button inside the error card also calls `generate`; it must work after a failure (re-enable in `finally`).

### UI-10 (Medium, Accessibility, Confirmed): the red and orange buttons fail the 4.5:1 contrast rule, the account "Reset" button badly (2.2:1)
**What a user would notice.** The destructive buttons are hard to read for anyone with low vision or on a dim screen: "Reset Account Data" is white text on orange, "Delete Account & All Data" and "Permanently Delete Everything" are white on bright red, and every `.btn-danger` button is red text on pale red.
**Evidence.** Measured in Chromium (text colour against the composited background), light / dark:
- "Reset Account Data" (`u-bg-v_color_warn u-c-v_color_on_brand`, `src/client/22_client-creator-profile.js:631`/`636`): **2.20 / 2.06**
- "Delete Account & All Data" and `#confirmDeleteAccountBtn` (`u-bg-v_color_danger u-c-v_color_on_brand`, `:636`, `:812`): **3.55 / 3.41**
- `.btn-danger` at rest (`color: var(--color-danger)` on `--color-danger-subtle`, `src/page/09_page-shell.js:3768-3769`): **3.01 / 4.06**; on hover (`--color-on-brand` on `--color-danger`, `:3781`): **3.55 / 3.41**
- the "+ Add" pill in light mode: 4.36; the "Remove" pill in dark mode: 4.23 (both just under, 13.6px text)
- white on `--accent` in dark mode (Ko-fi "Support" button `src/client/16_client-row-core.js:2433`, episode badge `src/client/19_client-search-and-likes.js:4102`): `#FFFFFF` on `#0A84FF` ≈ 3.7
Rule 9 of `docs/AI_UI_RULES.md` says contrast ≥ 4.5:1 and "never white text on `--color-brand/success/warn/danger`". `tests/design-system.test.mjs:87-93` only checks white on `--color-brand` inside CSS rule blocks, so `u-*` helper pairs and the danger/warn tokens are never checked.
**Root cause.** These spots use the raw status colours as fills (there is no `--color-danger-fill`/`--color-warn-fill`), and `.btn-danger` uses `--color-danger` where the `*-text` token exists for text.
**Fix.** (1) `.btn-danger` text: `var(--color-danger-text)` (the "Remove" pill's red already reaches 4.83 in light). (2) For the solid buttons, either switch them to `.btn-danger` (rule 1: reuse the component) or add `--color-danger-fill`/`--color-warn-fill` tokens dark enough for white text, as `--color-brand-fill` was done. (3) Use `--color-brand-fill` behind white text instead of `--accent`. Then extend the design-system test to check `--color-on-brand` against every `u-bg-v_color_*` it is paired with, and `.btn-danger` text against its background.
**Test.** Extend `tests/design-system.test.mjs`: for each `u-bg-v_<token>` that appears in the same class list as `u-c-v_color_on_brand`, and for `.btn-danger` rest/hover, compute the ratio from the token values and require ≥ 4.5 in light and dark. Fails today on the five cases above.
**Risk.** Look changes on purpose: run `node tests/ui-contract.mjs --update` and keep the diff. Check hover and pressed states too.

### UI-11 (Low, Accessibility, Confirmed): the like (♡) buttons and the webhook address box have no real name
**What a user would notice.** A screen-reader user hears "white heart suit, button" on every list card in Discover and Search, with no word "like" and no way to tell whether it is already liked (the only sign is ♡ vs ♥). The media-server webhook address in Settings → Tracking & Scrobble is read out as an unnamed text box.
**Evidence.** `src/client/19_client-search-and-likes.js:1082` and `:2282` build `<button type="button" class="lc-btn searchLikeExternalBtn…" data-url="…">&#9825;</button>` with no `aria-label` or `aria-pressed`; Chromium's accessibility tree gives `button "♡"`. The channel directory's copy does it right (`src/client/20_client-channel-builder.js:12322`, `aria-label="Like this channel"`). `src/client/22_client-creator-profile.js:1160` `<input type="text" readonly id="scrobbleWebhookInput" …>` has no label (`ariaSnapshot` → `textbox:` with no name). Rule 6 asks for `aria-label` on icon-only buttons. Also noted: the app page has no `<main>` landmark (`document.querySelectorAll('main').length === 0`), so "skip to main content" in a screen reader has nowhere to go.
**Root cause.** These two builders predate the icon-button rule; the channel builder copy was fixed, these were not.
**Fix.** Add `aria-label="Like this list"` and `aria-pressed="true|false"` to both builders (and keep `aria-pressed` in step where the click handler swaps ♡/♥); add `aria-label="Webhook address"` to the input. Optionally make the `.page` container a `<main>`.
**Test.** Extend `tests/client-escapes.test.mjs` or a new client test: render a Discover card and a search result, assert the like button has a non-empty `aria-label` and an `aria-pressed` value.
**Risk.** None.
