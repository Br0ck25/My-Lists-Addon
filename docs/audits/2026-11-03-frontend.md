## Summary for the owner
The app's screens hold up well. No page crashed in any test: not with the server failing, not with junk saved in the browser, not at any screen size from a small phone to a TV. Keyboard use, dark mode and the sign-in dialog all behave. Nothing here exposes or loses anyone's data.

What is wrong, in the order a user would feel it:

Fix UI-01 first: it is a one-line-per-form change and it makes every other server error visible again.

## Findings
### UI-01 (Medium, Error States, Confirmed): error messages open behind the form that caused them
**What a user would notice.** In Create List (and seven other pop-up forms), if the server refuses the save, nothing seems to happen: the form stays open and the "Could Not Save List" message is hidden behind it. Only after pressing Cancel does the message appear.
**Evidence.** `src/page/09_page-shell.js:5389` `<div id="createListModal" class="modal-overlay …" style="display:none; z-index:10001; …">`; the same inline `z-index:10001` is on `createCollectionModal`, `importNuvioCollectionsModal`, `syncNuvioModal`, `addShelfModal`, `importListModal`, `importChannelModal`, `selectListModal` (`grep -n 'z-index:10001' src/page/09_page-shell.js`, 8 hits). The message comes from `showModal()` (`src/client/16_client-row-core.js:2298`), whose `.modal-overlay` uses `z-index: var(--z-modal)` = 1000 (`src/page/09_page-shell.js:4677`, token at `src/core/00_constants.js:1858`). `src/client/22_client-creator-profile.js:6250` calls `showAppNoticeModal('Could Not Save List', …)` while `createListModal` is still open. Reproduced in Playwright: signed in, POSTs answered with 500 `{"ok":false,"error":"Server exploded"}`, Create List → Create. `document.elementsFromPoint` at the centre of the screen lists `#createListModal` (z 10001) above `#activeModalOverlay` (z 1000) holding "Could Not Save List / Server exploded / OK". No toast. Focus also moves into the hidden dialog (`showModal` focuses its heading), so a keyboard user is lost.
**Root cause.** The eight static forms were given a hard-coded `z-index:10001`, above the `--z-modal` layer every `showModal`/`appShellDialog`/`showAppNoticeModal` dialog uses, so any dialog opened from inside them stacks underneath.
**Fix.** Remove the inline `z-index:10001` from the eight static modals so they use `--z-modal` like every other dialog (later-appended `#activeModalOverlay` then sits on top by document order), or add one `--z-modal-raised` token for `#activeModalOverlay` if order is not enough. Do not add a new number.
**Test.** Client/Playwright test: open `createListModal`, call `showAppNoticeModal('x','y',true)`, assert `document.elementFromPoint(centre)` is inside `#activeModalOverlay`. Fails today. A guard in `tests/design-system.test.mjs` that no `z-index:` numeric literal appears in page HTML would also catch a repeat.
**Risk.** Check the mobile bottom nav (`--z-nav` 900) still sits below the forms, and that the forms still cover the sticky header.

**Verification.** Regression introduced. The original case is fixed: in Playwright against `node dev/server.mjs` (signed in, POSTs answered 500), Create List, then Create shows "Could Not Save List / Server exploded" on top (`elementFromPoint` at the centre is inside `#activeModalOverlay`) at 1280 and 360 px, light and dark; at the pre-fix commit 82d8263 it was under the form. But the fix makes stacking depend on document order, and the nine static forms sit before `#activeModalOverlay`, so a static form opened while a dialog is open now hides behind it. Reproduced: signed in, open `/?trakt_error=exchange_failed`; `src/client/17_client-my-lists-and-trakt-oauth.js:865-877` shows the "Trakt Connection" alert ("Opening direct PIN code activation instead...") and 500 ms later opens `#traktDeviceModal`. Before the fix the PIN form (z-index 10002) was on top; now the alert covers it until the person closes it. Still to do: a static form opened from a dialog (at least `traktDeviceModal`) must come up above it, for example by closing the alert before opening the PIN form, or by moving the form to the end of `body` when it opens. Add a test for that case.

### UI-04 (Medium, State Management, Confirmed): reloading the channel builder throws away the half-built channel, and reopens an empty builder even after signing out
**What a user would notice.** Someone half-way through building a channel who reloads, or whose phone reloads the tab, comes back to an empty "Create a Custom Channel" form with no warning that their picks were lost. After signing out, the Channels tab still opens on that empty builder (with "My Channels" ticked), and they only learn they need an account when they press save.
**Evidence.** `src/client/20_client-channel-builder.js:10107` stores `localStorage.setItem('myListAddon:channelsSubmenu', name)` with `name === 'build'` (from `openBuildCustomChannel`, `:10149`); the early restore (`src/client/16_client-row-core.js:241-262`) shows `#channelsSubBuild` for that value. The draft (`channelDraftItems`, `#channelNameInput`) is memory only, and `grep -rn beforeunload src` finds nothing. Reproduced: signed in → Channels → + Create Channel → typed a name → reload: builder visible, name empty. Then signed out → `/channels`: `channelsSubmenu` still `build`, builder still visible. Saving is still guarded (`requireSignedInFor('build channels')`, `:10127` and others), so nothing wrong is saved.
**Root cause.** The builder is remembered as a sub-tab, but its draft is not, and nothing checks the sign-in state when restoring it.
**Owner decision (2026-11-03).** After a reload the person stays in the builder and loses nothing they had put in. Raised from Low to Medium because it loses the user's work.
**Fix.** Save the draft as it changes: name, description, play order, broadcast settings, `channelDraftItems`, poster/backdrop and `editingChannelId`. Store it in `localStorage` under a key that includes the account name, e.g. `myListAddon:channelDraft:<creatorName>`. Drafts hold no credentials, so D-13 does not apply. On load with `channelsSubmenu === 'build'` and a draft for the signed-in account, reopen the builder and refill it with the existing setters (`applyChannelBroadcastSettings`, `setChannelPlayOrder`, the draft render). Clear the draft when the channel is saved, or when the person cancels or deletes it. Assumption to confirm in the fix session: when signed out, the builder is not shown (go to My Channels), and the draft waits under that account's key until they sign back in. That way a shared computer never shows one person's draft to another.
**Test.** Playwright: signed in, + Create Channel, type a name and add a title, reload. The builder is open with the same name and title. Save, reload: the builder is empty, or My Channels shows. Signed-out case: with `channelsSubmenu = build` and no key, My Channels is shown.
**Risk.** Low; the `?sub=build` deep link from the share flow should keep working.

**Verification.** Verified fixed. (The Fix progress table named commit f5c6d6d, which does not exist; the fix is 6a4dd60.)
